# Caslow 서비스 완성도 분석

이 문서는 Caslow를 실제 사용자가 장기간 이용하는 개인 가계부 서비스로 가정하고, 실제 Frontend 화면, 내비게이션, API client, FastAPI router, Supabase 접근, 통계·예산·AI·알림 코드를 기준으로 부족한 기능과 사용성 문제를 분석한 결과다.

분석상 제한:

- Supabase SQL migration/schema 파일이 없어 DB 구조는 실제 `.table(...)` 호출에서 확인된 범위만 판단했다.
- 외부 서비스 환경 변수와 운영 DB가 없어 Groq, Neo4j, SendGrid, Expo Push의 운영 성공 여부는 정적 코드 연결을 기준으로 판단했다.
- 이 문서에서 "구현됨"은 코드 경로가 존재하고 Frontend와 Backend가 연결되어 있다는 의미다.

## 핵심 결론

Caslow는 지출 CRUD, 예산, 목표, 통계, AI, OCR, 정기 지출까지 구현 범위가 넓다. 그러나 실제 사용자가 수개월 이상 사용하는 가계부로 보기에는 다음 기능이 크게 부족하다.

1. 수입과 잔액이 없다.
2. 이전·다음 월 이동과 과거 월 장부 조회가 없다.
3. 거래 검색과 날짜 범위 조회가 없다.
4. 월별 예산 이력이 없다.
5. 데이터 내보내기·백업·복구가 없다.

현재 단계는 기능이 풍부한 프로젝트형 프로토타입에 가깝고 장기간 사용하는 실서비스로는 보완이 필요하다.

## 1. 전체 서비스 사용자 흐름

### 회원가입

관련 파일:

- `frontend/src/screens/SignupScreen.tsx`
- `frontend/src/lib/supabase.ts`
- `frontend/App.tsx`

현재 구현:

- 이름·이메일·비밀번호·비밀번호 확인
- 이메일 형식과 비밀번호 길이 검증
- 비밀번호 일치 검증
- Supabase Auth 회원가입
- 중복 이메일 등 일부 오류 안내

부족한 기능과 불편:

- 가입 완료 전용 화면과 구체적인 이메일 인증 안내가 없다.
- 이용약관·개인정보처리방침 동의가 없다.
- 첫 사용자 온보딩이 없다.
- 가입 당시 입력한 이름을 확인·수정할 프로필 화면이 없다.

추천: 가입 완료 안내와 첫 로그인 온보딩을 제공한다.

우선순위: P1

### 로그인

관련 파일:

- `frontend/src/screens/LoginScreen.tsx`
- `frontend/src/screens/modals/ForgotPasswordModal.tsx`
- `frontend/src/lib/pushNotification.ts`

현재 구현:

- 이메일·비밀번호 로그인
- 입력 검증
- 잘못된 인증 정보·미인증 이메일·요청 과다 일부 구분

부족한 기능과 불편:

- 오프라인·네트워크 오류를 별도로 안내하지 않는다.
- 앱에서 Push 권한 상태를 확인할 수 없다.
- 로그인 상태에서 비밀번호를 변경하는 설정이 없다.

추천: 네트워크 오류를 구분하고 설정 화면에 Push 권한 상태와 비밀번호 변경을 추가한다.

현재 구현:

부족한 기능과 불편:

- 이전·다음 월 이동과 연도 변경이 없다.

### 수입 등록

현재 상태: 미구현

실제 코드에는 `ExpenseCreate`, `ExpenseUpdate`, `/expenses`만 있으며 수입 화면·API·테이블 접근이 없다. 거래 금액도 지출을 의미하는 `-₩`로 표시된다.

사용자 영향:

- 급여·용돈·환급·이자를 기록할 수 없다.
- 총수입·잔액·순현금흐름을 계산할 수 없다.
- 개인 가계부보다 지출 추적기에 가까워진다.

추천: 수입·지출 거래 유형, 수입 카테고리, 월 총수입·총지출·잔액을 추가한다.

우선순위: P0

저장 후에는 `navigation.navigate('HomeMain')`을 호출하지만 Expense stack에는 `HomeMain`이 없다.

[추정] React Navigation 상위 구조가 해당 route를 해석하지 못하면 입력 tab에서 저장 후 이동 실패나 navigation 경고가 발생할 수 있다.

사용자 영향: 저장 성공 후 입력 화면에 남거나 다시 저장해 중복 거래를 만들 수 있다.

추천: Root navigator 기준 홈 tab 이동 또는 명시적인 nested navigation을 사용한다.

우선순위: P0

### 현재 월만 조회 가능

[문제] `HomeScreen.tsx`는 `date.startsWith(currentMonth)`인 거래만 표시하며 선택 월 state와 이전·다음 버튼이 없다.

[사용자 영향] 과거 지출이 DB에 존재해도 홈에서 확인할 수 없다.

[추천 기능] 이전·다음 월, 연·월 picker, 선택 월 API 조회를 추가한다.

[우선순위] P0

### 과거 월 chart와 상세 장부가 연결되지 않음

[문제] `GET /expenses/analysis/monthly`는 최근 월 합계를 반환하지만 해당 월의 거래 목록을 열 수 없다.

[사용자 영향] 지난달 총액은 알 수 있지만 어떤 거래 때문인지 확인할 수 없다.

[추천 기능] Chart point 선택 시 해당 월 장부로 이동한다.

[우선순위] P0

### 로컬 시간과 UTC 혼용

[문제] 홈의 `today`는 local date지만 `currentMonth`는 `toISOString()` 기반 UTC다.

[사용자 영향] 한국 시간 월초 특정 시간대에 서로 다른 월을 가리킬 가능성이 있다.

[추천 기능] 날짜 계산을 local date 또는 `Asia/Seoul` 기준으로 통일한다.

[우선순위] P0

### 미래 거래가 저장 후 숨겨짐

[문제] Form은 미래 날짜를 허용하지만 홈은 `date <= today`인 거래만 표시한다.

[사용자 영향] 저장 성공 후 방금 입력한 거래를 찾지 못할 수 있다.

[추천 기능] 미래 날짜를 막거나 예정 거래로 분리한다.

[우선순위] P0

### 합계와 거래 건수 기준 불일치

[문제] 합계는 현재 월·오늘 이하 거래를 사용하고 건수는 현재 월 전체 거래를 사용한다.

[사용자 영향] 미래 거래가 있으면 표시된 건수와 합계의 범위가 다를 수 있다.

[추천 기능] 동일 데이터 집합을 사용하거나 예정 거래를 별도 표시한다.

[우선순위] P0

### 연도와 빈 달 표시

[문제] Chart label은 월만 표시하며 거래가 없는 달은 chart에서 빠진다.

[사용자 영향] 연도 경계와 0원인 달을 이해하기 어렵다.

[추천 기능] `25.12`, `26.01`처럼 연도를 표시하고 최근 6개월의 빈 달은 0원으로 채운다.

[우선순위] P1

반드시 필요한 개선:

1. 월별 예산 이력: 현재 `budgets`는 사용자당 단일 금액이라 과거 예산을 알 수 없다.

- 카테고리별 예산

- 남은 일수 기준 일일 사용 가능액

## 10. 개발하면서 놓친 기능 최종 목록

### 반드시 추가하는 것을 추천

1. 이전·다음 월 이동과 과거 월 상세 장부
2. 수입 등록과 총수입·총지출·잔액
3. 거래 검색과 날짜 범위 조회
4. 저장 중 중복 방지와 저장 후 navigation 수정
5. 미래 날짜·정기 지출 삭제 정책 정리

### 추가하면 사용성이 크게 좋아지는 기능

1. 전월 대비 지출 증감
2. 월별 예산 이력
3. Excel/CSV 내보내기와 backup
4. 정기 지출 수정·일시 중지
5. 빈 데이터·API 오류·재시도 화면

### 나중에 고도화하면 좋은 기능

1. 카테고리별 예산
2. AI 월말 결산
3. 결제수단·계좌
4. 앱 잠금·생체인증
5. 다크모드

### 개발자가 놓쳤을 가능성이 가장 높은 기능 TOP 10

1. **과거 월 상세 장부** — 월별 chart는 있지만 지난달 거래 목록에는 접근할 수 없다.
2. **수입과 잔액** — 화면·API·모델이 모두 지출 중심이다.
3. **거래 검색** — 사용 기간이 길어질수록 가장 먼저 문제가 된다.
4. **날짜 범위와 연도 조회** — 특정 기간 소비를 찾을 수 없다.
5. **미래 날짜 거래의 일관된 처리** — 저장은 되지만 홈에서는 숨겨진다.
6. **정기 지출 중지와 과거 기록 삭제 분리** — 규칙 삭제가 과거 거래까지 삭제할 수 있다.
7. **입력 tab 저장 후 navigation** — `ExpenseStack`에 없는 `HomeMain` 이동을 시도한다.
8. **빈 데이터와 API 오류 구분** — 서버 오류가 빈 장부처럼 보일 수 있다.
9. **월별 예산 이력** — 단일 예산만 저장해 과거 예산 성과를 복원할 수 없다.
10. **데이터 export·backup·복구** — 가져오기는 있지만 보관하거나 되돌릴 방법은 없다.

## 최종 결론

Caslow는 AI 기능을 더 추가하기 전에 다음 순서로 기본 가계부 기능을 완성하는 것이 좋다.

```text
수입·잔액
→ 월 이동·과거 조회
→ 검색·기간 filter
→ 데이터 안정성·오류 상태
→ 월별 예산과 비교 통계
→ backup·복구
→ AI·자동화 고도화
```

현재 Caslow에 가장 필요한 것은 기능 수를 늘리는 것이 아니라 이미 저장한 금융 데이터를 사용자가 언제든 정확히 찾고 비교하며 안전하게 관리할 수 있도록 만드는 것이다.
