# Caslow 개발 일지 - 2026-08-20

## 오늘의 목표

- 현재 월에 고정된 홈 장부를 연·월 단위로 조회할 수 있도록 개선한다.
- 기존 React Navigation, FastAPI router, Supabase 접근 구조를 유지하면서 변경 범위를 최소화한다.
- 월 이동 후 거래 목록, 합계, 예산이 선택한 월을 기준으로 함께 갱신되도록 한다.
- 작업 결과와 실제 검증 범위를 구분하여 기록한다.

## 작업 내용

### 1. 기존 월 조회 흐름 확인

- `frontend/src/screens/HomeScreen.tsx`에서 `getExpenses()`로 전체 거래를 받은 뒤 현재 월 문자열로 다시 필터링하는 구조를 확인했다.
- 조회 기준 월을 변경하는 상태와 이전·다음 월 이동 UI가 없었다.
- `frontend/src/lib/api.ts`의 거래 조회 함수와 `backend/routers/expenses.py`의 `GET /expenses/` 모두 연·월 파라미터를 받지 않는 것을 확인했다.
- 사용자에게 과거 거래 조회는 핵심 기능이므로 우선순위를 **P0**으로 판단했다.

### 2. 월별 거래 조회 API 추가

- `GET /expenses/?year={year}&month={month}` 형식으로 선택 월을 전달하도록 확장했다.
- `year`와 `month`는 함께 전달하도록 검증하고, 월은 1~12, 연도는 1900~2100 범위로 제한했다.
- 월 시작일 이상, 다음 달 시작일 미만 조건을 사용해 12월에서 다음 해 1월로 넘어가는 범위도 동일한 방식으로 처리했다.
- 파라미터가 없는 기존 호출은 전체 거래를 반환하도록 유지하여 기존 API 호출과의 호환성을 남겼다.

### 3. 홈 장부 월 이동 UI 및 상태 추가

- `frontend/src/screens/HomeScreen.tsx`에 선택 월을 나타내는 `viewDate` 상태를 추가했다.
- 이전 달, 다음 달, 이번 달 이동 UI를 추가했다.
- 현재 정책에서는 미래 월 이동을 허용하지 않으므로 현재 월에서 다음 달 버튼을 비활성화했다.
- 월이 바뀌면 선택한 연·월로 거래와 예산을 다시 조회하도록 연결했다.
- 기존의 현재 월 고정 필터를 제거하고 서버가 반환한 선택 월 데이터를 기준으로 합계와 건수를 계산하도록 변경했다.
- 빠르게 월을 전환할 때 이전 API 응답이 새로운 월의 데이터를 덮어쓰지 않도록 거래와 예산 요청에 요청 식별값을 적용했다.

### 4. 빈 달과 오류 상태 처리

- 선택한 월에 거래가 없으면 `{월}월 지출 내역이 없습니다.` 안내를 표시하도록 했다.
- 거래 조회 실패 시 오류 메시지와 `다시 시도` 버튼을 표시하도록 했다.
- 새로운 월을 조회하는 동안 직전 월 거래가 선택한 월의 데이터처럼 잠시 노출되지 않도록 기존 거래 상태를 비운 뒤 로딩하도록 변경했다.

### 5. 선택 월 거래 등록 및 수정 복귀 흐름

- 홈 장부의 추가 버튼에서 선택한 연·월을 `ExpenseForm`으로 전달하도록 했다.
- 과거 월에서 등록할 경우 현재 일자를 해당 월의 유효한 마지막 날짜 이내로 보정하여 초기 날짜를 생성하도록 했다.
- 저장 후 거래 날짜 또는 전달받은 복귀 연·월을 기준으로 홈 장부에 돌아가도록 변경했다.
- 상세 화면에서 수정 화면으로 이동할 때 기존 장부의 연·월을 함께 전달하도록 했다.
- 입력 탭의 `ExpenseForm`이 탭 전환 뒤에도 유지되어 이전 입력값이 남을 가능성을 확인했다. 각 신규 입력에 `formSessionId`를 전달하고 새 세션에서 입력값을 초기화하도록 보완했다.

### 6. 입력값과 미래 날짜 검증

- 제목은 공백만 입력할 수 없도록 검증했다.
- 금액은 1원 이상의 정수만 저장할 수 있도록 검증했다.
- 저장 중 버튼을 비활성화하여 중복 요청 가능성을 줄였다.
- Frontend 날짜 선택기의 최대 날짜를 오늘로 제한했다.
- 직접 날짜를 입력하는 Web 환경과 API 직접 호출도 고려하여 Frontend와 Backend 모두 미래 날짜 등록·수정을 거부하도록 했다.

### 7. 월별 예산 구조 확장

- 기존 `budgets` 조회와 저장이 사용자당 단일 행만 가정하는 구조임을 확인했다.
- `GET /budget/?year={year}&month={month}`와 월 정보가 포함된 `POST /budget/`으로 API를 확장했다.
- `budgets`에 `year`, `month`를 추가하고 `(user_id, year, month)`를 고유 키로 사용하는 migration을 작성했다.
- 선택 월에 예산이 없으면 `amount: 0`, `is_set: false`를 반환하도록 했다.
- 지출 등록 후 예산 초과 알림이 시스템 현재 월이 아니라 등록한 거래의 연·월 예산과 지출 합계를 사용하도록 변경했다.
- AI 채팅과 AI 인사이트의 예산 조회도 현재 연·월 예산을 조회하도록 수정했다.

### 8. 분석 차트에서 월 장부 이동

- `frontend/src/screens/AnalysisScreen.tsx`의 월별 차트 데이터에 원본 `YYYY-MM` 값을 유지하도록 했다.
- 차트의 데이터 포인트를 누르면 해당 연·월을 홈 장부에 전달하도록 연결했다.

### 9. 발견 문제 보완 구현

- 홈의 선택 월에서 기존 `BudgetModal`을 재사용해 해당 월 예산을 설정·수정하도록 연결했다.
- 예산이 없는 달은 `예산 미설정` 상태로 구분하고 조회 실패 시 재시도 동작을 제공했다.
- 카테고리 통계 API와 분석 화면에 연·월 파라미터를 추가했다.
- 월별 추이는 선택 월까지 연속 6개월을 반환하고 거래가 없는 달도 `0원`으로 포함하도록 변경했다.
- AI 인사이트는 선택 월 통계와 혼동되지 않도록 `이번 달 AI 인사이트`로 표시했다.
- Neo4j는 현재 월 AI 검색용 예산만 저장하고, 과거 월 예산 수정으로 현재 예산 노드가 덮이지 않도록 했다.
- Web 날짜 직접 입력에서 존재하지 않는 날짜를 거부하도록 연·월·일 일치 검증을 추가했다.
- 저장 완료 안내의 확인 버튼을 누른 뒤 선택 월 장부로 이동하도록 변경했다.
- `backend/migrations/verify_monthly_budgets.sql`에 누락값, 중복값, 월 범위, RLS, 인덱스 확인 쿼리를 추가했다.

## 발견한 문제

### 문제 1. 과거 월 장부 조회 불가

- 문제: 홈 화면이 시스템 현재 월만 필터링하여 표시하고 월 이동 수단을 제공하지 않았다.
- 원인: Frontend에 선택 월 상태가 없고 거래 API도 연·월 조회 조건을 지원하지 않았다.
- 사용자 영향: 사용자가 이전 달과 이전 연도의 거래 기록을 확인하기 어려웠다.
- 우선순위: P0
- 상태: **부분 구현** — 코드 변경은 완료했으나 실제 앱과 서버 연동 테스트가 필요하다.

### 문제 2. 월별 예산 분리 불가

- 문제: 예산이 사용자당 하나의 값으로 저장되어 과거 월 장부와 현재 예산이 섞일 수 있었다.
- 원인: `budgets` 테이블과 API가 연·월 구분값을 사용하지 않았다.
- 사용자 영향: 과거 월을 조회할 때 해당 월의 예산 대비 지출을 정확히 표현할 수 없었다.
- 우선순위: P0
- 상태: **확인 필요** — 코드와 migration은 작성했으나 실제 Supabase DB에는 아직 적용하지 않았다.

### 문제 3. 입력 화면 재진입 시 이전 상태 잔존 가능성

- 문제: 입력 탭의 Stack이 유지되면 저장 전 입력 상태가 다음 등록에 남을 가능성이 있었다.
- 원인: 화면이 다시 마운트된다는 가정으로 초기 상태가 `useState`에서 한 번만 설정됐다.
- 사용자 영향: 새 거래 등록 화면에 이전 제목, 금액, 날짜가 남아 잘못 저장할 수 있다.
- 우선순위: P1
- 상태: **부분 구현** — 신규 입력 세션 식별값으로 초기화하도록 수정했으며 실제 탭 재진입 테스트가 필요하다.

### 문제 4. 미래 거래 처리 기준 부재

- 문제: 날짜 선택과 API 저장 단계에서 미래 거래를 제한하지 않았다.
- 원인: Frontend와 Backend 모델 저장 전 미래 날짜 검증이 없었다.
- 사용자 영향: 미래 거래가 현재 월 합계나 알림에 포함되어 사용자가 예상하지 못한 결과가 발생할 수 있었다.
- 우선순위: P1
- 상태: **부분 구현** — Frontend와 Backend 제한 코드는 추가했으나 플랫폼별 날짜 입력 테스트가 필요하다.

## 남은 문제 / 확인 필요

- `backend/migrations/001_monthly_budgets.sql`을 애플리케이션 코드보다 먼저 Supabase에 적용해야 한다. 적용하지 않고 새 Backend를 배포하면 `budgets.year`, `budgets.month` 조회가 실패한다.
- 기존 예산 데이터는 migration 실행 시 실행 날짜의 연·월 예산으로 보정된다. 이 기준이 실제 사용자 데이터와 맞는지 배포 전에 확인해야 한다.
- 설정 화면은 현재 월 예산을 편집하고 홈 화면은 선택한 과거 월 예산도 편집하도록 역할을 나눴다. 실제 모바일 화면에서 동작 확인이 필요하다.
- Neo4j는 현재 월 예산 projection만 유지하도록 기준 연·월을 추가했다. 과거 월 AI 분석을 도입할 때는 월별 Graph 모델 확장이 별도로 필요하다.
- 실제 Supabase 테스트 환경에서 RLS가 월별 예산 insert/update를 허용하는지 확인해야 한다.
- `npm ci` 결과 34건의 의존성 취약점(낮음 2, 보통 11, 높음 19, 치명적 2)이 보고됐다. 자동 `audit fix`는 호환성 검토 없이 실행하지 않았다.
- 현재 작업은 코드 및 정적 흐름 기준으로 검증했으며 **실제 동작 확인 완료 상태가 아니다**.
